Option 1: Browser extension Recommended · No command line · All platforms

Use a small browser extension to sync the muse.ai login session from your own computer, where you are already logged in. No Python, no terminal, no commands.
Why an extension is required: all 4 core muse.ai cookies are marked httpOnly, so page scripts (typing document.cookie in F12, bookmarklets) cannot read them; only a browser extension's cookies API can.
1
Download and unzip the extension
Unzip it into a folder you won't delete, e.g. D:\muse2api-extension.
⬇ Download muse2api-extension.zip
2
Load the extension in your browser
Using Chrome as an example (steps are similar for Edge / Brave / other Chromium-based browsers):
  1. Type chrome://extensions in the address bar and press Enter
  2. Turn on the Developer mode switch in the top-right corner
  3. Click Load unpacked in the top-left corner
  4. Select the folder unzipped in step 1 (not a single file inside it)
3
Log in to muse.ai, then click the extension icon to import
First open https://muse.ai/ in your own browser and log in (until you can see the chat interface), then click the extension icon in the browser toolbar, fill in the two values below, and click "Read & import".

Option 2: Copy manually No install · Fallback

If you don't want to install the extension, you can extract the cookie string by hand. The key is to use the request headers in the Network panel, not the Console — the cookie: request header line includes the httpOnly cookies, which the Console cannot read.
  1. Open and log in to https://muse.ai/ in your own browser, and stay on the chat page
  2. Press F12 to open DevTools and switch to the Network panel
  3. Press F5 to reload the page so the request list is populated
  4. Click any muse.ai request in the list (the first one is fine)
  5. On the right, open Headers → scroll down to Request Headers
  6. Find the line starting with cookie: and copy the whole string after the colon (from hatch_sess= to the end of the line)
  7. Paste it into the input box in "Option 3" below and click Import
Note: use cookie: from the request headers, not the "response headers". set-cookie in the response headers only contains some of the cookies, so things will be missing.

Cookie lifetimes Measured

Measured lifetimes of each muse.ai cookie (may vary slightly between accounts):
cookiehttpOnlyMeasured lifetimePurpose
hatch_sessYes~30 daysMain session; determines whether you are logged in
hatch_gwYes~1 yearGateway token
hatch_vmlYes~2 daysShort-lived verification token; determines account lifetime
hatch_native_auth_deviceYes~30 daysDevice identifier (anonymous visitors have it too; not a login credential)
How long does an account actually last? It depends on the core cookie that expires first, namely hatch_vml — about 2 days.
Note: these 2 days are NOT extended by heavier use. After each generation, this service does read back the new cookies issued by muse.ai and writes them to the account pool (which is why you will see the "Expires" column update), but the expiry of the core cookies is not pushed back (confirmed by before/after generation experiments).
So: you need to re-import roughly every 2 days. Fortunately it's quick — just click the extension icon.
Import several accounts at once: the pool rotates by "least recently used", so more accounts are more stable and spread out the re-imports (one per day, instead of all accounts expiring at the same time).
When should you re-import? When the "Expires" column shows Expired, the status shows Error, or the "Missing core" tag appears.

Integration guide

The API follows the OpenAI style; downstream projects only need to change base_url and api_key.
BASE URL: —

1. Available models

Model IDPurposeEndpoint
muse-sparkText / code chat (streaming supported)POST /v1/chat/completions
POST /v1/responses
muse-imageText-to-image / image editingPOST /v1/images/generations
muse-videoText-to-video / image-to-videoPOST /v1/videos → GET /v1/videos/{id}
These three are the real capabilities of the Muse family: Muse Spark (language / code), Muse Image (images), Muse Video (videos). The muse.ai web app is an auto-routing agent with no model picker in the UI, so the model field is only for downstream compatibility — common names such as gpt-4o, claude-sonnet-4, dall-e-3 are automatically mapped to the matching capability.

2. Chat / coding

Copy# Non-streaming
curl -X POST "BASE/v1/chat/completions" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"muse-spark","messages":[{"role":"user","content":"Write a quicksort in Python"}]}'

# Streaming: add "stream":true; returns standard SSE (data: {...} / data: [DONE])

3. Image generation (curl)

Copycurl -X POST "BASE/v1/images/generations" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"A Shiba Inu wearing an astronaut helmet","size":"1:1","response_format":"url"}'

# Response
{"created":1790148495,"data":[{
  "revised_prompt":"A Shiba Inu wearing an astronaut helmet",
  "url":"http://your-server:18610/v1/media/xxxx.webp",
  "kind":"image","bytes":23860}]}

# url is a full absolute URL that downstream apps can render / download directly; /v1/media/* needs no auth.
# For base64, pass "response_format":"b64_json".

4. Video generation (curl, async)

Copy# ① Create a task
curl -X POST "BASE/v1/videos" \
  -H "Authorization: Bearer $MUSE2API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"A kitten walking on the grass","duration":5,"size":"16:9"}'
# → {"id":"task_xxx","status":"queued"}

# ② Poll for the result
curl "BASE/v1/videos/task_xxx" -H "Authorization: Bearer $MUSE2API_KEY"
# → {"status":"succeeded","result":{"url":"/v1/media/xxx.mp4"}}

5. Python (openai SDK compatible)

Copyfrom openai import OpenAI
import time

client = OpenAI(base_url="BASE/v1", api_key="m2a_...")

# Image generation
r = client.images.generate(model="muse-image", prompt="A Shiba Inu wearing an astronaut helmet")
print(r.data[0].url)

# Video generation (uses the native endpoint because it is an async task)
import requests
t = requests.post("BASE/v1/videos", json={"prompt":"A kitten walking","duration":5},
                  headers={"Authorization":"Bearer m2a_..."}).json()
while True:
    s = requests.get(f"BASE/v1/videos/{t['id']}",
                     headers={"Authorization":"Bearer m2a_..."}).json()
    if s["status"] in ("succeeded","failed"): break
    time.sleep(5)
print(s)

7. Authentication

Except for /healthz, /readyz and /v1/media/*, all endpoints require Authorization: Bearer <API Key>. The API Key is configured in MUSE2API_KEY in /opt/muse2api/.env on the server.

8. Connecting clients / agents

Any client that supports a "custom OpenAI-compatible endpoint" works with just three values:
SettingValue
Base URL / API addresshttp://<your server IP or domain>:18610/v1
API Keym2a_... (the one under "Connection info" at the top of this page)
Model namemuse-spark
Any model name works: common names (gpt-4o, gpt-5, claude-sonnet-4, deepseek-chat, gemini-2.5-pro, etc.) are mapped to the matching capability; unknown names are passed through as-is. muse.ai routes automatically anyway, so results are unaffected.

Compatibility by client type

Client typeRequired capabilityStatus

Autonomous agent modes that need "tool calling"tool_calls / function calling⚠️ Not supported
About the "tool calling" limitation (important, verified):
The muse.ai web assistant has an explicit alignment policy that refuses to "output fake tool-call JSON" — in testing it literally replied "I won't output 'fake tool calls' in this JSON format — I don't have a get_weather tool". Three prompt protocols with different wording and placement were tried, and all failed.
So: autonomous agent modes that rely on tool_calls (the kind that read/write files and run commands automatically) cannot be supported; but all Q&A-style usage — chat, coding, explanation, translation, summarization, image and video generation — works fully.
If a client sends a tools field anyway, the API won't error; it ignores the tool declarations and answers as a normal chat.
